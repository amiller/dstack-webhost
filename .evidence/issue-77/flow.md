**Tier:** 2-style walk of the published parity board, driven through a real tee-daemon
(deploy → serve → Playwright walk). The daemon here is the suite's local instance
(started by `test_daemon.py`'s own harness with a 2-slot browser pool), not
webhost-staging: **no staging credentials exist in this sandbox** (searched
`~/.tee-daemon*.env`, `~/paseo-batch/.env`, `*/.staging-env` — none present for this
uid; box-inventory documents them in the operator's home only). The staging walk of
the published board is the operator-run remainder, same shape as the one below.

## What was walked (2026-08-29)

1. `parity/` (the board generated by `PARITY_BASE=… python browser_parity.py`, bespoke
   side = the live deployed twitter-debug at `https://pod.dstack.soc1024.com/twitter-debug`,
   public probes only) was deployed as a static project through the daemon's own seam:
   `POST /_api/projects` (multipart) → project `parity-board`.
2. `GET /parity-board/` serves the board; body asserts `"CUTOVER: NOT READY"`.
3. Playwright (real Chromium) opened the page and asserted:
   - 9 table rows = header + all 8 capability rows (inject jar, logged-in screenshot,
     DOM reify, driven actions, write/post, egress binding, liveness, isolation);
   - the cutover banner renders `CUTOVER: NOT READY` with the rule
     *"bespoke Brave is NOT retired and the flag is NOT flipped until every row is
     green, including isolation"*;
   - the isolation row shows the bespoke side `CANNOT` (structural: one global
     session) and the pool side's independently-asserted checks;
   - the liveness row is the one GREEN row (pool `PASS` via a real
     `POST /_api/browser/render` lease + bespoke `PASS` from the live
     `/twitter/health`).

## Board content asserted by this walk (from `parity/board.json`)

- Pool side driven ONLY through `POST /_api/browser/render` + `GET /_api/browser/pool`;
  every render response records its lease result (`lease.id`, `slot`, `render_ms`) —
  a pool health check alone is never counted as parity.
- Isolation: two concurrent leases (x.com `@parity-tw` + youtube.com `@parity-yt`),
  pool `busy == 2` observed mid-render, each read only its own account, jar-less
  read after reset returns empty.
- NOT-YET rows carry their exact missing dependency: live logged-in jar
  (operator OAuth3 vault connect — `/twitter/setjar` no longer exists), RFC 0018
  broker (#50), per-lease egress lock (unimplemented), X-Debug-Secret for bespoke
  writes. The bespoke egress probe recorded a datacenter IP (Hurricane Electric),
  not a VPN — surfaced, not hidden.
- `parity/shots/bespoke-x-home.png` is the bespoke engine's real signed-out frame
  (proves serving; names the wall). No personal data is committed.

## Acceptance mapping

- repeatable e2e command over both engines → `browser_parity.py` (+ wired into
  `test_daemon.py` on a 2-slot pool; suite green end-to-end).
- one board row per capability → 8 rows, published at `parity/index.html` + `board.json`.
- daemon seam + lease/bridge result recorded → liveness row + every pool evidence cell.
- two-subject isolation, bespoke recorded as unable to pass → isolation row.
- seeded-jar/screenshot/reify rows NOT-YET with exact dependencies, never green by default.
- board records that retirement/flag-flip waits for all-green incl. isolation → banner + `cutover.rule`.
