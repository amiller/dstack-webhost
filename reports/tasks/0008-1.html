Task 0008-1: Standardize multipart deploy API format

RFC: 0008-consistent-deploy-api | Status: done | Commit: b7c19ef4

Task Overview

Task 0008-1 addresses a critical interoperability problem between the running daemon on the CVM and the repository code. The RFC 0008: Consistent Multipart Deploy API identifies that the production daemon expects multipart/form-data requests with a manifest field and optional files fields, while the newer codebase expected a simple JSON body.

What the RFC Asked For

From RFC 0008's Implementation section:

3. Update the repo version to match the running daemon's expectations:
   - `manifest` field: JSON string with project name, runtime type, ports, env vars
   - `files` field(s): uploaded files (tar, zip, or individual files)
4. Add validation: reject requests missing required fields with clear error messages
5. Add backward compatibility: if a JSON body is sent (old format), wrap it in the multipart format internally
6. Document the API contract in a docstring on the handler

Why This Matters

The mismatch made it impossible to deploy to the running daemon using the repo's own client code. Without fixing this, development workflows would be broken and testing against production would be impossible. The solution establishes multipart/form-data as the canonical format while maintaining backward compatibility for existing JSON-based clients.

What Changed

proxy/ingress.py

The _api_deploy() method in the Ingress class was completely rewritten to support dual request formats.

Before (Original Implementation)

async def _api_deploy(self, request: web.Request) -> web.Response:
    manifest = await request.json()
    project = await deploy(
        self.store, self.docker, self.audit_manager, self.tracker, self.rtm, manifest)
    return web.json_response(asdict(project), status=201)

This was a simple implementation that only handled JSON requests via await request.json(). No validation of required fields was performed, and multipart/form-data was not supported at all.

After (New Implementation)

async def _api_deploy(self, request: web.Request) -> web.Response:
    """
    Deploy API endpoint.

    Accepts two request formats:

    1. multipart/form-data (canonical format):
       - manifest: JSON string containing project name, source, ref, runtime, etc.
       - files: uploaded files (optional, currently only git source is supported)

    2. application/json (backward compatible):
       - Direct JSON body with manifest fields

    Example multipart request:
       curl -F "manifest=@manifest.json" https://<ingress>/_api/projects

    Example JSON request:
       curl -H "Content-Type: application/json" -d '{"name":"test","source":"https://github.com/user/repo"}' https://<ingress>/_api/projects
    """
    content_type = request.headers.get("Content-Type", "")

    if "multipart/form-data" in content_type:
        # Handle multipart/form-data format (canonical)
        try:
            reader = await request.multipart()
            manifest_str = None
            files_received = []

            async for field in reader:
                if field.name == "manifest":
                    manifest_str = await field.text()
                elif field.name == "files":
                    # Read file content (currently not used, but kept for future compatibility)
                    content = await field.read()
                    files_received.append(content)

            if not manifest_str:
                return web.json_response(
                    {"error": "missing manifest field in multipart request"},
                    status=400
                )

            # Parse manifest JSON string
            try:
                manifest = json.loads(manifest_str)
            except json.JSONDecodeError as e:
                return web.json_response(
                    {"error": f"malformed JSON in manifest field: {str(e)}"},
                    status=400
                )

            # Validate required fields
            if "name" not in manifest:
                return web.json_response(
                    {"error": "missing required field 'name' in manifest"},
                    status=400
                )

            if "source" not in manifest:
                return web.json_response(
                    {"error": "missing required field 'source' in manifest"},
                    status=400
                )

        except Exception as e:
            return web.json_response(
                {"error": f"error processing multipart request: {str(e)}"},
                status=400
            )
    else:
        # Handle JSON body format (backward compatible)
        try:
            manifest = await request.json()
        except json.JSONDecodeError:
            return web.json_response(
                {"error": "invalid JSON in request body"},
                status=400
            )

        # Validate required fields for JSON format
        if "name" not in manifest:
            return web.json_response(
                {"error": "missing required field 'name'"},
                status=400
            )

        if "source" not in manifest:
            return web.json_response(
                {"error": "missing required field 'source'"},
                status=400
            )

    # Deploy the project
    project = await deploy(
        self.store, self.docker, self.audit_manager, self.tracker, self.rtm, manifest)
    return web.json_response(asdict(project), status=201)

Key Design Decisions

  • Content-Type Detection: Uses a substring check "multipart/form-data" in content_type to handle variations like charset parameters
  • Async Iterator Pattern: Uses await request.multipart() and async for field in reader for efficient streaming of large uploads
  • Field-by-Field Processing: Iterates through all form fields to find manifest and files, allowing for flexibility in field order
  • Dual Validation Paths: Both multipart and JSON paths validate name and source fields, but with slightly different error messages to help debug which format was attempted
  • Graceful Degradation: The files field is read but not currently used, preserving future compatibility for file-based deployments
  • Error Handling: Catches exceptions broadly at the multipart processing level and returns detailed error messages

How It Works

The deploy API now follows this flow:

  1. Request Reception: The _api_deploy() handler receives the incoming POST request to /_api/projects
  2. Content-Type Inspection: The method checks the Content-Type header to determine the request format
  3. Format Branching:
    • Multipart path: If multipart/form-data is detected:
      • Creates an async multipart reader
      • Iterates through all form fields
      • Extracts the manifest field as text
      • Optionally reads files fields
      • Validates that manifest exists
      • Parses the manifest JSON string
      • Validates name and source fields
    • JSON path: Otherwise (backward compatibility):
      • Parses the entire request body as JSON
      • Validates name and source fields
  4. Deploy Invocation: Both paths converge at the deploy() function call with the parsed manifest
  5. Response: Returns the created project as JSON with status 201

Data Structures Involved

The manifest is expected to contain project configuration fields:

  • name (required): Project identifier
  • source (required): Git repository URL
  • ref (optional): Git branch, tag, or commit
  • runtime (optional): Runtime type (e.g., "deno", "static")
  • entry (optional): Entry point file
  • port (optional): Port number
  • mode (optional): Deployment mode ("dev" or "attested")
  • env (optional): Environment variables

Integration with Existing Code

The new implementation integrates seamlessly with the existing codebase:

  • The deploy() function from proxy/deploy.py is called exactly as before
  • All existing middleware, authentication, and error handling remain unchanged
  • The response format is identical to the original implementation
  • The Ingress class structure is preserved

Testing & Verification

Success Cases

1. Multipart Deployment (Canonical Format)

cat > manifest.json <<'EOF'
{
  "name": "test-project",
  "source": "https://github.com/example/repo",
  "ref": "main",
  "runtime": "deno",
  "entry": "mod.ts"
}
EOF

curl -F "manifest=@manifest.json" \
     http://localhost:8000/_api/projects

Expected response: {"name": "test-project", ...} with status 201

2. JSON Deployment (Backward Compatibility)

curl -H "Content-Type: application/json" \
     -d '{"name":"test-project","source":"https://github.com/example/repo"}' \
     http://localhost:8000/_api/projects

Expected response: {"name": "test-project", ...} with status 201

Error Cases

1. Missing Manifest in Multipart Request

curl -F "files=@somefile.txt" \
     http://localhost:8000/_api/projects

Expected response: {"error": "missing manifest field in multipart request"} with status 400

2. Malformed JSON in Manifest

curl -F "manifest={invalid json" \
     http://localhost:8000/_api/projects

Expected response: {"error": "malformed JSON in manifest field: ..."} with status 400

3. Missing Required Field (name)

curl -F "manifest={\"source\":\"https://github.com/example/repo\"}" \
     http://localhost:8000/_api/projects

Expected response: {"error": "missing required field 'name' in manifest"} with status 400

4. Missing Required Field (source)

curl -F "manifest={\"name\":\"test\"}" \
     http://localhost:8000/_api/projects

Expected response: {"error": "missing required field 'source' in manifest"} with status 400

5. Invalid JSON Body

curl -H "Content-Type: application/json" \
     -d '{invalid}' \
     http://localhost:8000/_api/projects

Expected response: {"error": "invalid JSON in request body"} with status 400

Edge Cases & Error Handling

  • Large file uploads: The async reader handles streaming, so large files won't block the event loop
  • Multiple manifest fields: Only the last manifest field is used (standard multipart behavior)
  • Charset in Content-Type: The substring check handles multipart/form-data; charset=utf-8 correctly
  • Empty manifest: Results in JSON decode error with clear message
  • Unexpected fields: Additional fields are ignored (not validated, not rejected)

Verification of Deployment

After a successful deployment, verify the project is running:

# Check the project status
curl http://localhost:8000/_api/projects/test-project

# Access the deployed application
curl http://localhost:8000/test-project/

Issues & Follow-ups

Known Limitations

  • Files field unused: While the files field is read from multipart requests, its contents are not currently utilized. The deploy flow still relies on git cloning from the source URL. Future work could support direct tar/zip deployments using this field.
  • No file size limits: The implementation doesn't enforce size limits on uploaded files, which could lead to resource exhaustion in production.
  • No content validation: Beyond parsing JSON, the manifest structure is minimally validated (only checking for name and source). Invalid values for other fields will only be caught downstream in the deploy function.

Dependencies on Other Tasks

This task has minimal dependencies on other RFCs but is related to:

  • RFC 0009 (runtime health checks): While technically a separate task, the commit for 0008-1 also added the /_health endpoint to the Deno router. These features work together to provide a more robust deployment experience.
  • Existing deploy infrastructure: This task builds upon the existing deploy() function in proxy/deploy.py, which handles git cloning, container management, and project storage.

Incomplete Items

The RFC's report requirements mention documenting the API contract, which has been partially addressed by the detailed docstring. However, formal API documentation beyond the docstring was not included in this implementation.

Note: The commit b7c19ef4 also removed the health_check() function from runtimes.py that was present in earlier versions. This suggests task 0009-1 may have been partially implemented or reverted during the development of 0008-1. The health check endpoint was re-added to the Deno router inline, but the Python-side health checking logic was removed.

Summary

Task 0008-1 successfully resolved the deploy API format mismatch between the running CVM daemon and the repository code. The implementation establishes multipart/form-data as the canonical format while maintaining backward compatibility with JSON-based clients. The code includes comprehensive validation, clear error messages, and detailed documentation via the expanded docstring.

While the files field support is currently dormant, the infrastructure is in place for future enhancements like direct file-based deployments. The implementation follows aiohttp best practices with async streaming and proper error handling.
