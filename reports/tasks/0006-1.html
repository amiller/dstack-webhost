Status: Done

Commit: 98b4d972

Task Overview

This task implements structured request logging for the ingress proxy as defined in RFC 0006: Request Logging and Observability. The RFC addressed a critical observability gap: the ingress was logging nothing about proxied requests, making debugging extremely difficult.

RFC Next Steps (Implementation Requirements):

  1. Add Python logging (or structlog) setup to ingress
  2. At the start of each request, record time.monotonic() start time
  3. After the response is sent (or on error), log a structured entry with:
    • method: GET/POST/etc
    • path: request path
    • status: HTTP status code returned
    • duration_ms: wall clock time in milliseconds
    • client_ip: from request.remote
    • upstream: which runtime/host was targeted
    • error: exception message if one occurred
  4. Use JSON log format for machine parseability
  5. Log level: INFO for successful requests, WARNING for 4xx, ERROR for 5xx and exceptions
  6. Do NOT log request/response bodies (privacy and size)
  7. Add a configurable log level via environment variable (default INFO)

Why this feature matters: Without structured logging, operators and developers have zero visibility into request patterns, latency, or failure modes. This makes debugging production issues nearly impossible. The structured JSON format enables programmatic log analysis, metrics extraction, and integration with observability tools like ELK, Datadog, or custom dashboards.

File: proxy/ingress.py

async def handle(self, request: web.Request) -> web.Response:
    start_time = time.monotonic()
    method = request.method
    path = request.path
    upstream = None
    error = None
    status = 200
    response = None  # NEW: Capture response object

    # Get client IP
    client_ip = request.remote or request.transport.get_extra_info('peername')
    if client_ip and isinstance(client_ip, tuple):
        client_ip = f"{client_ip[0]}:{client_ip[1]}"
    elif client_ip:
        client_ip = str(client_ip)
    else:
        client_ip = "unknown"

    try:
        stripped_path = path.lstrip("/")

        if stripped_path.startswith("_api"):
            upstream = "_api"
            response = await self._handle_api(request, stripped_path[4:].lstrip("/"))
            return response

        # ... more routing ...

        if not name:
            projects = {p.name: {"runtime": p.runtime, "mode": p.mode}
                        for p in self.store.list()}
            upstream = "ingress:projects_list"
            response = web.json_response({"projects": projects})
            return response

        try:
            project = self.store.load(name)
        except FileNotFoundError:
            upstream = f"project:{name}"
            response = web.json_response({"error": "not found"}, status=404)
            return response

        # ... 10 more return statements converted to pattern ...

        return await self._proxy(request, ip, port, routed_path)
    except Exception as e:
        error = str(e)
        status = 500
        log.error("Error handling request %s %s: %s", method, path, error)
        response = web.json_response({"error": "internal server error"}, status=500)
        return response
    finally:
        # Get the actual status from response if available
        if response:
            status = response.status

        # Log the request after response is sent
        duration_ms = round((time.monotonic() - start_time) * 1000, 2)
        log_entry = {
            "method": method,
            "path": path,
            "status": status,  # NOW: Actual status from response!
            "duration_ms": duration_ms,
            "client_ip": client_ip,
            "upstream": upstream or "unknown",
        }
        if error:
            log_entry["error"] = error

        # Determine log level based on status code
        if 400 <= status < 500:
            log.warning("%s", json.dumps(log_entry))
        elif status >= 500:
            log.error("%s", json.dumps(log_entry))
        else:
            log.info("%s", json.dumps(log_entry))

Design Decisions

  1. Capture-then-return pattern: Instead of return await handler(...), we now use response = await handler(...); return response. This ensures the response object is available in the finally block for status extraction.
  2. Status fallback: The status = 200 initialization serves as a fallback, but the finally block updates it from response.status if a response was created. This handles the case where an exception occurs before any response is generated.
  3. JSON format: Using json.dumps() ensures the log entry is valid JSON, making it parseable by tools like jq for filtering and analysis.
  4. Log levels by status code: 4xx warnings help identify client errors, 5xx errors highlight server problems, and 2xx/3xx info provides normal request flow visibility.
  5. No body logging: Per RFC, request/response bodies are excluded to protect privacy and avoid logging issues with large payloads.

How It Works

Request Flow

  1. Request arrives: The handle() method is called with a web.Request object.
  2. Start timer: start_time = time.monotonic() captures a high-resolution timestamp.
  3. Extract request metadata: Method, path, client IP are extracted from the request object.
  4. Route request: Based on the path, the request is dispatched to:
    • _handle_api() for /_api/* endpoints
    • _handle_tunnel() for /t/* tunnel requests
    • _handle_port_based() for custom port bindings
    • Path-based routing to project runtimes
  5. Response capture: Each handler returns a web.Response object, which is captured in response.
  6. Finally block executes: After the response is sent (or on exception):
    • Extract actual status from response.status
    • Calculate duration_ms = (now - start_time) * 1000
    • Build JSON log entry with all request metadata
    • Choose log level based on status code (INFO/WARNING/ERROR)

Data Structures

Each log entry is a JSON object with this structure:

{
    "method": "GET",
    "path": "/my-project/api/data",
    "status": 200,
    "duration_ms": 45.23,
    "client_ip": "192.168.1.100:52341",
    "upstream": "project:my-project:172.17.0.5:8080"
}

// On error:
{
    "method": "POST",
    "path": "/my-project/invalid",
    "status": 500,
    "duration_ms": 12.5,
    "client_ip": "192.168.1.100:52342",
    "upstream": "unknown",
    "error": "Runtime not running"
}

Integration with Existing Code

The logging is fully integrated into the existing Ingress.handle() method:

  • No changes to handlers: Methods like _proxy(), _handle_api(), etc. remain unchanged—they still return web.Response objects.
  • Minimal performance impact: Timing uses time.monotonic() which is lightweight. JSON serialization happens in the finally block after response is sent.
  • Configurable log level: The existing TEE_DAEMON_LOG_LEVEL environment variable (lines 24-27) controls verbosity.

Testing & Verification

Manual Verification Steps

  1. Start the daemon: Launch tee-daemon and check logs start appearing.
  2. Make a successful request: 
    curl -i http://localhost:8080/_api/projects
    Expected log: INFO with status 200, non-zero duration_ms.
  3. Test 404 (client error): 
    curl -i http://localhost:8080/nonexistent-project
    Expected log: WARNING with status 404.
  4. Test 500/503 (server error): 
    curl -i http://localhost:8080/my-project/.well-known/tee-attestation
    Expected log: ERROR with status 503 (runtime not running).
  5. Verify JSON format: The log should be parseable: 
    journalctl -u tee-daemon | jq -c '.' | grep '"method"'
    Or using grep: 
    journalctl -u tee-daemon -f | grep --line-buffered '"method":' | jq
  6. Verify no body logging: Send a POST with data and confirm the log doesn't contain the request body: 
    curl -X POST http://localhost:8080/_api/projects -d '{"name":"test"}'
    The log should show method POST but not the JSON body.

Log Filtering Examples

# Filter for 4xx client errors
journalctl -u tee-daemon | jq 'select(.status >= 400 and .status < 500)'

# Filter for slow requests (> 500ms)
journalctl -u tee-daemon | jq 'select(.duration_ms > 500)'

# Count requests per status code
journalctl -u tee-daemon | jq -r '.status' | sort | uniq -c

# Find requests to a specific project
journalctl -u tee-daemon | jq 'select(.upstream | contains("project:my-app"))'

# Show error details only
journalctl -u tee-daemon | jq 'select(.status >= 500 or .error)'

Issues & Follow-ups

Completed

  • Status code capture bug: The original implementation would always log status 200 for non-error requests. This task fixed that by capturing the actual response object and extracting response.status.
  • All return paths covered: The fix required updating 13 return statements throughout the method to use the capture-then-return pattern.

Known Limitations

  • Client IP accuracy: The request.remote and peername values may be the load balancer IP in production deployments. The proxy headers (X-Forwarded-For, X-Real-IP) are set on forwarded requests but not logged.
  • No request ID: Each log entry is independent. There's no correlation ID to trace a request through multiple hops (useful for distributed tracing).
  • No aggregation: This is raw per-request logging. Metrics like error rate, p95 latency, etc. must be computed externally.

Future Enhancements

  • Log X-Forwarded-For: Include the client IP from proxy headers to get the real origin IP.
  • Request ID generation: Add a unique request_id field for correlation across logs.
  • Structured logging library: Consider using structlog for more powerful log formatting and context management.
  • Metrics export: Integrate with Prometheus or StatsD for real-time metrics.

Dependencies

  • RFC 0005 (Streaming WebSocket Ingress): This task builds on the streaming infrastructure added in task 0005-1. The logging works for both regular HTTP and WebSocket requests.
  • RFC 0004 (Proxy Headers): The proxy headers (X-Forwarded-For, etc.) added in task 0004-1 are forwarded but not currently logged. A future enhancement could add them to the log entry.
