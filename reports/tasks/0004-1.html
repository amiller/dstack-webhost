Task 0004-1: Add X-Forwarded-For and proxy headers to ingress

Task ID: 0004-1
Title: Add X-Forwarded-For and proxy headers to ingress
RFC: 0004-ingress-proxy-headers
Status: done
Commit: ed297b7a

Task Overview

This task implements RFC 0004, which adds standard proxy headers to the ingress proxy in proxy/ingress.py. The RFC specifically requires:

"In _proxy(), before forwarding the request to the upstream runtime:

  1. Set headers["X-Forwarded-For"] to the request's remote address
  2. Set headers["X-Forwarded-Proto"] based on whether the original request was HTTP or HTTPS
  3. Set headers["X-Real-IP"] to the same remote address
  4. If X-Forwarded-For already exists (from an upstream proxy), append to it rather than replacing"

Why This Feature Matters

Before this implementation, the ingress proxy did not add any proxy headers when forwarding requests to runtimes. This meant that downstream applications saw the internal Docker IP (e.g., 172.19.0.3:3000) as the client address, breaking:

  • IP-based access control and rate limiting
  • Geolocation services
  • Audit logging requiring true client identification
  • Security incident analysis

What Changed

Modified File: proxy/ingress.py

The implementation added proxy header handling to two methods:

  1. _proxy() (line 168) — handles project routing
  2. Tunnel handler (line 308+ in get_tunnel_handler()) — handles temporary tunnel access

Changes in _proxy() (lines 168-204)

Before: The method simply filtered out certain headers and forwarded the request.

async def _proxy(self, request: web.Request, ip: str, port: int,
                 path: str) -> web.Response:
    body = await request.read()
    headers = {k: v for k, v in request.headers.items()
               if k.lower() not in ("host", "transfer-encoding", "accept-encoding")}

    url = f"http://{ip}:{port}{path}"

After: Added 23 lines of proxy header injection logic:

async def _proxy(self, request: web.Request, ip: str, port: int,
                 path: str) -> web.Response:
    body = await request.read()
    headers = {k: v for k, v in request.headers.items()
               if k.lower() not in ("host", "transfer-encoding", "accept-encoding")}

    # Add proxy headers
    client_ip = request.remote or request.transport.get_extra_info('peername')
    if client_ip and isinstance(client_ip, tuple):
        client_ip = f"{client_ip[0]}:{client_ip[1]}"
    elif client_ip:
        client_ip = str(client_ip)

    if client_ip:
        # Handle chained proxies by appending to existing X-Forwarded-For
        existing_xff = headers.get("X-Forwarded-For")
        if existing_xff:
            headers["X-Forwarded-For"] = f"{existing_xff}, {client_ip}"
        else:
            headers["X-Forwarded-For"] = client_ip
        headers["X-Real-IP"] = client_ip

    # Set X-Forwarded-Proto based on the request scheme
    # Check for existing X-Forwarded-Proto header first (chained proxies)
    existing_proto = headers.get("X-Forwarded-Proto")
    if not existing_proto:
        headers["X-Forwarded-Proto"] = request.scheme

    url = f"http://{ip}:{port}{path}"

Changes in Tunnel Handler (lines 308-367)

The exact same proxy header logic was added to the tunnel handler, ensuring that requests routed through temporary tunnels also receive proper client identification headers.

Design Decisions

DecisionRationale
Use request.remote with fallback to request.transport.get_extra_info('peername') request.remote is the primary source of client IP in aiohttp, but the transport-level peername provides a reliable fallback in edge cases
Include port in client IP string when available When peername returns a tuple (ip, port), both values are included. This provides more complete connection information for debugging
Append to existing X-Forwarded-For rather than replace Supports chained proxy scenarios. If an upstream proxy (e.g., cloud load balancer) already set this header, we preserve that chain by appending our hop
Only set X-Forwarded-Proto if not already present Prevents overwriting protocol information from upstream proxies that may have TLS termination
Applied to both _proxy() and tunnel handler Ensures consistent behavior across all ingress paths—regular project routing and temporary tunnel access

How It Works

Request Flow

  1. Request arrives at ingress: A client makes an HTTP request to the ingress proxy
  2. Client IP extraction: The proxy extracts the client IP using request.remote or falls back to transport peername
  3. Header processing:
    • If X-Forwarded-For exists, append the current client IP with comma separator
    • If not, create new X-Forwarded-For with the client IP
    • Set X-Real-IP to the immediate client IP
    • If X-Forwarded-Proto doesn't exist, set it based on request.scheme
  4. Forward to backend: The request (with added headers) is forwarded to the runtime container
  5. Backend processing: The runtime can now access real client information from the headers

Data Structures and APIs

  • aiohttp web.Request: The source of request.remote, request.scheme, and request.headers
  • Header dictionary: A standard Python dict modified before being passed to aiohttp.ClientSession.request()
  • Client IP formats:
    • String from request.remote: direct IP or ip:port
    • Tuple from peername: (ip_string, port_integer)

Integration Points

The proxy headers are inserted at a critical point—immediately after header filtering and before creating the upstream HTTP request. This ensures:

  • Headers are preserved through the proxy chain
  • No downstream code needs modification to access client information
  • Both regular project routing and tunnel access paths are covered

Verification Method 1: Test Endpoint That Returns Headers

Deploy a simple Deno/Node.js application that returns all request headers as JSON:

import { serve } from "https://deno.land/std@0.200.0/http/server.ts"

serve((req) => {
  const headers: Record = {}
  for (const [key, value] of req.headers.entries()) {
    headers[key] = value
  }
  return new Response(JSON.stringify(headers, null, 2), {
    headers: { "content-type": "application/json" }
  })
}, { port: 8080 })
