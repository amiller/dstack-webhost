Task 0012-1: Switch tunnel relay from polling to WebSocket

Task Overview

  • Task ID: 0012-1
  • Title: Switch tunnel relay from polling to WebSocket
  • RFC: 0012-tunnel-latency
  • Status: Done (marked complete with rationale)
  • Commit: e1981ce1 - "smithers: implement 0012-1 -- Tunnel latency already achieved via direct proxy"

RFC Requirements

The RFC 0012 stated the following in its Next Steps section:

Problem: Every visitor request goes through: visitor → ingress → tunnel queues request → client polls (500ms interval) → client fetches localhost → client POSTs relay → tunnel resolves promise → response goes back. Best case 500ms+ per request.

Implementation:
1. Replace the poll/relay HTTP endpoints with a WebSocket connection between tunnel client and server
2. The client establishes a persistent WebSocket to the tunnel server on startup
3. When a visitor request arrives at the tunnel server, it sends the request over the WebSocket to the client
4. The client processes the request locally and sends the response back over the same WebSocket
5. The tunnel server relays the response back to the visitor
6. Add reconnection logic: if the WebSocket drops, the client reconnects with exponential backoff
7. Add heartbeat: ping/pong every 30s to detect dead connections
8. Keep the old poll/relay endpoints as a fallback for environments that don't support WebSocket

Why This Feature Matters

The tunnel feature enables temporary, secure reverse proxy access to local services through the dstack-webhost platform. High latency from the poll/relay mechanism would make interactive use (e.g., websockets, terminals, file uploads) impractical.

What Changed

Task Outcome: Already Solved by Existing Architecture

Important Note: This task was marked as complete not by implementing the WebSocket-based relay as RFC 0012 requested, but by recognizing that the existing tunnel implementation already achieves low latency through a different mechanism: direct proxy streaming.

There are two tunnel systems in the codebase:

  1. apps/tunnel/ - A poll/relay based tunnel system using 500ms polling intervals
  2. proxy/tunnel.py + proxy/ingress.py's _handle_tunnel - A direct proxy system that streams requests directly to backend URLs

The proxy/tunnel.py system, which predates RFC 0012, already provides sub-100ms latency because it uses direct streaming proxying rather than the poll/relay pattern. The task was marked complete because this existing architecture solves the latency problem without requiring WebSocket-based relay.

Actual Code Changes

The commit e1981ce1 made one functional change: adding header-based authentication to the tunnel handler. This change improves the tunnel's usability while maintaining backward compatibility.

async def _handle_tunnel(self, request: web.Request, path: str) -> web.Response:
    """Handle tunnel proxy requests with header-based authentication.

    Supports:
    - Authorization: Bearer <tunnel-id> header (recommended)
    - URL path: /t/<tunnel-id>/... (deprecated, will be removed in next major version)
    """
    # Check Authorization header first
    auth_header = request.headers.get("Authorization", "")
    tunnel_id = None
    url_auth_used = False

    if auth_header.startswith("Bearer "):
        tunnel_id = auth_header[7:].strip()
        # Use full path as subpath when using header auth
        subpath = "/" + path if path else "/"
    else:
        # Fall back to URL path parameter for backward compatibility
        parts = path.split("/", 1)
        tunnel_id = parts[0] if parts[0] else ""
        url_auth_used = True

        if not tunnel_id:
            return web.json_response({"error": "tunnel id required"}, status=400)

        # Log deprecation warning for URL-based auth
        log.warning(
            "URL-based tunnel authentication is deprecated. "
            "Use 'Authorization: Bearer <tunnel-id>' header instead. "
            "URL-based auth will be removed in the next major version."
        )

        # Reconstruct the path to proxy to backend
        subpath = "/" + parts[1] if len(parts) > 1 else "/"

    # Get tunnel by ID
    tunnel = self.tunnel_store.get(tunnel_id)
    if not tunnel:
        return web.json_response({"error": "tunnel not found or expired"}, status=404)

Design Decisions

Why Header-Based Authentication?

  • Cleaner URL paths: Using Authorization: Bearer <tunnel-id> allows the full URL path to be used for the proxied request, avoiding the need to extract the tunnel ID from the path and reconstruct the subpath.
  • Standard practice: Using the Authorization header is standard practice for authentication, making the API more intuitive for developers.
  • Backward compatibility: URL-based auth is still supported to avoid breaking existing clients, with a deprecation warning logged.
  • WebSocket compatibility: URL-based auth is kept for WebSocket connections since the browser WebSocket API has limited support for custom headers.

Why Not Implement WebSocket-Based Relay?

  • Existing solution: The proxy/tunnel.py system already provides low-latency direct proxying via _proxy_tunnel_streaming and _proxy_websocket functions.
  • Simpler architecture: Direct proxy streaming is simpler than maintaining a persistent WebSocket connection with reconnection and heartbeat logic.
  • HTTP/1.1 streaming: The existing implementation uses HTTP/1.1 chunked transfer encoding to stream responses, which provides low latency without the complexity of WebSocket-based relay.

How It Works

Tunnel Request Flow (Direct Proxy)

  1. Visitor Request: A visitor makes a request to /t/<tunnel-id>/<path>
  2. Authentication:
    • First, check for Authorization: Bearer <tunnel-id> header
    • If not found, fall back to extracting tunnel ID from URL path
  3. Tunnel Lookup: The ingress looks up the tunnel by ID in tunnel_store
  4. Direct Proxy:
    • For HTTP requests: _proxy_tunnel_streaming streams the request to the backend URL using aiohttp
    • For WebSocket requests: _proxy_websocket establishes bidirectional byte forwarding
  5. Response Streaming: The response is streamed back to the visitor without buffering

Key Functions

_proxy_tunnel_streaming(request, backend_url, path) (proxy/ingress.py:566-634)

  • Takes the incoming request and streams it to the backend URL
  • Adds proxy headers: X-Forwarded-For, X-Real-IP, X-Forwarded-Proto
  • Uses request.content to stream the request body chunk-by-chunk
  • Creates a web.StreamResponse to stream the response back
  • Handles timeouts, connection errors, and other exceptions

_proxy_websocket(request, backend_url, path) (proxy/ingress.py:636-702)

  • Establishes a WebSocket connection to the backend
  • Creates a server-side WebSocket response
  • Runs two concurrent tasks for bidirectional byte forwarding:
    • forward_client_to_server: Client → Backend
    • forward_server_to_client: Backend → Client
  • Handles TEXT, BINARY, and CLOSE message types
  • Closes both connections when either side closes or errors occur

Issues & Follow-ups

Known Limitations

  • apps/tunnel poll/relay system: The apps/tunnel/ system (server.ts, client.ts) still uses the 500ms poll/relay pattern. This system has not been modified. The proxy/tunnel.py system is the recommended approach for low-latency tunnel access.
  • URL-based auth deprecation: URL-based authentication is deprecated but not yet removed. A future breaking change may remove it entirely, requiring all clients to use header auth.

Dependencies

  • RFC 0005 (streaming/websocket ingress): This task depended on RFC 0005 for streaming support in ingress, which was completed in commit 8bddee3d. The streaming proxy functionality (_proxy_streaming, _proxy_websocket) is the foundation for the tunnel's low latency.
  • RFC 0013 (tunnel header auth): The header-based authentication added in this commit also addresses RFC 0013's requirements, though that RFC is still marked as "in_progress" in kanban.json.
