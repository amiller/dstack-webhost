Task 0011-1: Add git clone validation to ensure non-empty directory

Task Overview

Task ID: 0011-1
Title: Add git clone validation to ensure non-empty directory
RFC: 0011-git-in-deno-runtime

What the RFC Asked For

From RFC 0011, Next Steps:

1. Add RUN apt-get update && apt-get install -y git && rm -rf /var/lib/apt/lists/* to the Deno runtime Dockerfile
2. In the deploy code that handles git clone: check the exit code of git clone and return a clear error if it fails
3. Add a validation step after clone: verify the target directory is non-empty (catches "clone succeeded but empty repo" case)
4. Rebuild the Docker image and update the running container

Why This Feature Matters

The RFC identified a critical silent failure mode: git-clone-based deploys were succeeding but creating empty directories. This happened because the system would complete the deploy process even when no files were actually cloned from the repository. Users would deploy expecting their code to run, but instead get an empty directory, leading to confusing runtime failures. Adding proper validation ensures users receive clear, actionable error messages when git operations fail.

What Changed

File: proxy/deploy.py

Modified the git_clone() function to add validation that ensures the cloned directory exists and is non-empty.

Before (lines 57-65 in commit b66f58ea^):

    _, stderr = await proc.communicate()
    if proc.returncode != 0:
        raise ValueError(f"git clone failed: {stderr.decode().strip()}")
    proc2 = await asyncio.create_subprocess_exec(
        "git", "-C", dest, "rev-parse", "HEAD",
        stdout=asyncio.subprocess.PIPE)
    stdout, _ = await proc2.communicate()
    return stdout.decode().strip()

After (lines 57-69 in commit b66f58ea):

    _, stderr = await proc.communicate()
    if proc.returncode != 0:
        raise ValueError(f"git clone failed: {stderr.decode().strip()}")
        # Validate cloned directory is non-empty
    if not os.path.exists(dest):
        raise ValueError(f"git clone succeeded but destination directory does not exist: {dest}")
    if not os.listdir(dest):
        raise ValueError(f"git clone succeeded but destination directory is empty: {dest}")
    proc2 = await asyncio.create_subprocess_exec(
        "git", "-C", dest, "rev-parse", "HEAD",
        stdout=asyncio.subprocess.PIPE)
    stdout, _ = await proc2.communicate()
    return stdout.decode().strip()

Design Decisions

Two validation checks instead of one: The implementation includes both os.path.exists(dest) and os.listdir(dest) checks. This provides more specific error messages for two different failure scenarios:

  • Missing directory: Git clone succeeded somehow, but no directory was created (should be rare, but catches edge cases)
  • Empty directory: Directory exists but has no files—this is the primary issue the RFC aimed to solve

Error messages after successful exit code: The validation runs after the proc.returncode != 0 check. This means we first catch explicit git failures (network errors, authentication failures, etc.) and then validate the result. This two-stage approach provides clear differentiation between "git failed" and "git succeeded but produced invalid output."

Validation location: The validation happens before the git rev-parse HEAD command, which would fail anyway on an empty directory. By validating first, we get a more descriptive error message and fail faster.

Architecture Note: The git clone operation runs on the host daemon system (inside the tee-daemon container), not inside the Deno runtime container. The main Dockerfile for tee-daemon already includes git installation (line 2 of Dockerfile). Therefore, RFC item #1 (adding git to Deno Dockerfile) was not necessary for this architecture. The files are made available to runtime containers via bind mounts.

How It Works

Invocation Flow

The git_clone() function is invoked during the deploy process in the deploy_project() function (line 142 of proxy/deploy.py):

files_dir = store.files_dir(name)
commit_sha = await git_clone(source, ref, files_dir)

Complete Function Flow:

  1. Setup: Function receives source (git URL), ref (branch/tag), and dest (target directory)
  2. Clean existing: If destination directory exists, remove it (line 48-49)
  3. Build git command: Construct git clone --depth 1 [--branch <ref>] <url> <dest>
  4. Execute git clone: Run subprocess and capture stdout/stderr (lines 55-57)
  5. Check exit code: If non-zero, raise error with stderr (lines 58-59)
  6. NEW: Validate directory exists: Check if os.path.exists(dest), raise error if false (lines 61-62)
  7. NEW: Validate non-empty: Check if os.listdir(dest) returns files, raise error if empty (lines 63-64)
  8. Get commit SHA: Run git rev-parse HEAD to get the actual commit (lines 65-69)
  9. Return: Return commit SHA string (line 69)

Data Structures and APIs

Input:

  • source: str - Git repository URL (can be full URL or bare repo name)
  • ref: str - Git branch, tag, or commit (optional)
  • dest: str - Local filesystem path for clone

Output:

  • str - The 40-character SHA of the cloned commit

Exceptions:

  • ValueError - Raised with descriptive message for any failure

Integration with Existing Code

The git_clone() function is part of the deploy pipeline that:

  1. Receives a deploy request via POST /_api/projects
  2. Validates the manifest (either from request body or project.json in repo)
  3. Calls git_clone() to fetch source code
  4. Detects runtime, entry point, and configuration
  5. Computes tree hash for verification
  6. Runs build steps (e.g., npm install)
  7. Saves project metadata
  8. Refreshes runtime container

Edge Cases and Error Handling

Bad credentials Error with git stderr Error with git stderr (unchanged)
Git returns 0 but no files Deploy "succeeds", empty directory, runtime error later Clear error: "git clone succeeded but destination directory is empty"

Issues & Follow-ups

Implementation Notes

Note on RFC Scope: The RFC requested adding git to Deno Dockerfile, but actual architecture runs git operations in the proxy container (not the runtime containers). The proxy container's Dockerfile already includes git. The implemented solution addresses the core problem (silent empty directories) through validation, which is architecturally simpler and covers all runtimes, not just Deno.

Known Limitations

  • No authentication handling: The system doesn't support private repositories with credentials (no SSH key or token support)
  • Depth 1 clone only: Uses --depth 1 for shallow clones; full history not available
  • No submodule support: Git submodules would not be cloned

Dependencies on Other Tasks

  • Independent task: This task has no dependencies on other tasks and can be deployed independently
  • Follows task 0008-1: Uses the standardized deploy API format from task 0008-1
