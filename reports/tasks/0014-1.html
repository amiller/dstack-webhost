What the RFC Asked For

From RFC 0014: Volume Mount Path Configuration, the Next Steps specified:

  1. When the router imports a project's module, set process.env.__PROJECT_DIR (or Deno.env.set) to the absolute path of the project's files directory
  2. Update the handler template/documentation to use Deno.env.get("__PROJECT_DIR") instead of new URL('.', import.meta.url).pathname
  3. Keep import.meta.url as a fallback if the env var isn't set (backward compat)

Why This Feature Matters

The Deno handler previously used import.meta.url to find sibling files, but the exact path depends on how the router mounts and imports modules. The router imports from /daemon-vol/projects/<name>/files/server.ts so import.meta.url resolves to that directory. This worked but was fragile — any change to the mount structure would break handlers.

By providing the project directory as an environment variable (__PROJECT_DIR), handlers get a stable, explicit path that is independent of the internal mount structure. This makes the system more robust against internal refactoring while maintaining backward compatibility.

New Project Directory Environment Variable Section

Added comprehensive documentation for using __PROJECT_DIR across all supported runtimes:

### Project Directory Environment Variable

Your handler has access to the project's files directory via the `__PROJECT_DIR` environment variable.
This is the recommended way to access project files, as it's independent of the mount structure.

**Deno/Bun (recommended):**
```typescript
export default async (req: Request, ctx: {env: Record}) => {
  const projectDir = ctx.env.__PROJECT_DIR || Deno.env.get("__PROJECT_DIR");
  const filePath = `${projectDir}/data/config.json`;
  const content = await Deno.readTextFile(filePath);
  return new Response(content);
};
```

**Node.js:**
```javascript
module.exports = (req, res, env) => {
  const projectDir = env.__PROJECT_DIR || process.env.__PROJECT_DIR;
  const fs = require('fs');
  const content = fs.readFileSync(`${projectDir}/data/config.json`);
  res.send(content);
};
```

**Python:**
```python
def handle(method, path, headers, body, env):
    project_dir = env.get("__PROJECT_DIR") or os.environ.get("__PROJECT_DIR")
    with open(f"{project_dir}/data/config.json") as f:
        content = f.read()
    return (200, {"Content-Type": "application/json"}, content.encode())
```

**Backward Compatibility (fallback):**
For older code using `import.meta.url` (Deno/Bun), you can use this pattern:
```typescript
const projectDir = Deno.env.get("__PROJECT_DIR") || new URL('.', import.meta.url).pathname;
```

Design Decision: The documentation shows two ways to access the environment variable:
1. ctx.env.__PROJECT_DIR — passed via the context object (preferred for handler pattern)
2. Deno.env.get("__PROJECT_DIR") — direct Deno environment access (fallback)
The fallback pattern ensures backward compatibility with existing code using import.meta.url.

How It Works

Flow Overview

The implementation adds project directory information during the handler loading phase. Here's the flow:

  1. Runtime Initialization: When a runtime container starts, it initializes its router (Deno, Node.js, or Python router embedded in runtimes.py).
  2. Project Discovery: The router scans the /projects directory for project manifests.
  3. Manifest Parsing: For each project found, the router reads /projects/{name}/project.json to get the manifest.
  4. Environment Injection: The router creates a copy of the manifest's env object (or an empty object if none exists) and injects __PROJECT_DIR = /projects/{name}/files.
  5. Module Loading: The handler module is imported from /projects/{name}/files/{entry}.
  6. Handler Registration: The loaded handler is registered in the handlers map along with its environment object containing __PROJECT_DIR.
  7. Request Handling: When a request arrives for a project, the handler receives the environment object containing __PROJECT_DIR.

Integration with Existing Code

The change is completely backward compatible:

  • Handlers that don't use project files continue to work unchanged.
  • Handlers using import.meta.url can be updated gradually.
  • The new __PROJECT_DIR environment variable is available immediately without any code changes needed in the handlers.
Note: The __PROJECT_DIR path follows the Docker volume mount structure. When runtime containers start, they mount the daemon's volume at /projects, giving them direct access to project files. The environment variable simply tells handlers where their specific project's files are located.

Edge Cases & Error Handling

  • Empty manifest.env: If the manifest has no env field, an empty object is created and __PROJECT_DIR is added to it.
  • Project with custom env: If the manifest already has environment variables, __PROJECT_DIR is added alongside them without overwriting.
  • Missing __PROJECT_DIR: The documentation shows fallback patterns using || or or operators to handle cases where the variable might not be set.
