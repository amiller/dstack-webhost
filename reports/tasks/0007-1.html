Task Overview

Task Information

  • Title: Implement Deno runtime hot-reload on file change
  • Source RFC: RFC 0007: Deno Runtime Hot-Reload
  • Implementation Commit: 87743b2a

RFC Requirements

RFC 0007 asked for hot-reload functionality to solve a critical developer experience problem:

"When a new project is deployed via multipart upload, files are written to the shared volume but the running deno container's import() caches the old module. rtm.refresh() recreates the container, but only when the LAST project using that runtime is torn down. Adding a new project to an already-running container does nothing — the router's initial module scan already ran."

The RFC specified the following implementation approach (Option A, recommended):

  1. In the Deno router, after initial module scan, start Deno.watchFs() on the projects directory
  2. On file change event, debounce 500ms (to batch rapid writes), then re-import the changed module
  3. If the new module fails to import, keep the old version running and log the error
  4. Send a signal back to the ingress that the reload completed (optional)

Why This Matters

Without hot-reload, developers had to perform a painful workflow to iterate on code:

  1. Deploy project changes
  2. Tear down ALL projects on the runtime
  3. Wait for the container to die
  4. Redeploy everything

Hot-reload enables rapid iteration by automatically detecting file changes and reloading modules without requiring container restarts. This is essential for developer productivity and for the platform's usability.

Why: A variable to store the timeout ID is needed for debouncing. This allows us to cancel pending reloads when new file changes occur, preventing multiple rapid reloads.

Change 2: Refactored Load Logic into Reusable Function

Before: 
for await (const entry of Deno.readDir("/projects")) {
  if (!entry.isDirectory || entry.name.startsWith("_")) continue;
  try {
    const raw = await Deno.readTextFile(`/projects/${entry.name}/project.json`);
    const manifest = JSON.parse(raw);
    if (manifest.runtime !== "deno" && manifest.runtime !== "bun") continue;
    const entryFile = manifest.entry || "server.ts";
    const mod = await import(`file:///projects/${entry.name}/files/${entryFile}?t=${Date.now()}`);
    const handler = mod.default;
    if (typeof handler === "function") {
      handlers.set(entry.name, handler);
      envs.set(entry.name, manifest.env || {});
      console.log(`Loaded: ${entry.name}`);
    }
  } catch (e) {
    console.error(`Failed to load ${entry.name}: ${e.message}`);
  }
}
After: 
async function loadProject(name: string): Promise<boolean> {
  try {
    const raw = await Deno.readTextFile(`/projects/${name}/project.json`);
    const manifest = JSON.parse(raw);
    if (manifest.runtime !== "deno" && manifest.runtime !== "bun") return false;
    const entryFile = manifest.entry || "server.ts";
    const mod = await import(`file:///projects/${name}/files/${entryFile}?t=${Date.now()}`);
    const handler = mod.default;
    if (typeof handler === "function") {
      handlers.set(name, handler);
      envs.set(name, manifest.env || {});
      console.log(`Loaded: ${name}`);
      return true;
    }
    return false;
  } catch (e) {
    console.error(`Failed to load ${name}: ${e.message}`);
    return false;
  }
}

Why: The original inline load logic was refactored into a reusable loadProject() function that returns a boolean success/failure indicator. This function can now be called during both initial load and reload operations.

Key design decision: The function returns true on success and false

Change 3: Added Safe Reload Function

New code added: 
async function reloadProject(name: string) {
  console.log(`Reloading: ${name}`);
  const oldHandler = handlers.get(name);
  const oldEnv = envs.get(name);
  const success = await loadProject(name);
  if (!success && oldHandler) {
    console.log(`Keeping old handler for ${name} (reload failed)`);
    handlers.set(name, oldHandler);
    if (oldEnv) envs.set(name, oldEnv);
  }
}

Why: This function implements the "keep old module on import failure" requirement from the RFC. It:

  1. Saves the current handler before attempting to reload
  2. Attempts to load the new version
  3. If loading fails and an old handler exists, restores the old handler

This ensures that syntax errors or bugs in new code don't break the running service — the old, working version continues to serve requests.

Change 4: Added Full Rescan Function

New code added: 
async function reloadAllProjects() {
  const seen = new Set<string>();
  for await (const entry of Deno.readDir("/projects")) {
    if (!entry.isDirectory || entry.name.startsWith("_")) continue;
    seen.add(entry.name);
    await reloadProject(entry.name);
  }
  // Remove projects that no longer exist
  for (const name of handlers.keys()) {
    if (!seen.has(name)) {
      console.log(`Removed: ${name}`);
      handlers.delete(name);
      envs.delete(name);
    }
  }
  console.log(`Router ready: ${handlers.size} projects`);
}

Why: This function:

  1. Scans all projects in the /projects directory
  2. Reloads each project (new or existing)
  3. Cleans up handlers for projects that no longer exist on disk
  4. Logs the final count of loaded projects

This enables full project lifecycle management — new projects are loaded, existing ones are reloaded, and deleted ones are removed.

Change 5: Changed Initialization to Use Reload Function

Before: 
// (The inline for-loop from Change 2 was here)
console.log(`Router ready: ${handlers.size} projects`);
After: 
// Initial load
await reloadAllProjects();

Why: Instead of having duplicate code for initial load and reload, we now use the same reloadAllProjects() function for both. This ensures consistency and reduces code duplication.

Change 6: Added File Watcher with Debouncing

New code added: 
// Watch for file changes with 500ms debounce
for await (const event of Deno.watchFs("/projects", { recursive: true })) {
  if (event.kind === "modify" || event.kind === "create" || event.kind === "remove") {
    const path = event.paths[0] || "";
    const match = path.match(/^\/projects\/([^\/]+)/);
    if (match) {
      const projectName = match[1];
      if (projectName && !projectName.startsWith("_")) {
        if (reloadTimeout !== null) clearTimeout(reloadTimeout);
        reloadTimeout = setTimeout(() => {
          reloadAllProjects();
          reloadTimeout = null;
        }, 500);
      }
    }
  }
}

Why: This is the core of the hot-reload feature. It:

  1. Uses Deno's watchFs() API to watch the /projects directory recursively
  2. Filters for modify, create, and remove events
  3. Extracts the project name from the file path using a regex
  4. Filters out projects starting with "_" (internal projects)
  5. Debounces reloads by clearing any pending timeout and setting a new 500ms timeout

Key design decision: Using 500ms debounce as specified in the RFC. This batches rapid file writes (e.g., when deploying multiple files at once) into a single reload operation.

How It Works

Initialization Flow

1. Router starts → 2. Call reloadAllProjects() → 3. Scan /projects directory → 4. For each project: call loadProject() → 5. Store handler in handlers Map → 6. Store env vars in envs Map → 7. Start Deno.serve() → 8. Start file watcher loop

Hot-Reload Flow

1. File change detected by Deno.watchFs() → 2. Extract project name from path → 3. Clear pending timeout (if any) → 4. Set 500ms timeout → 5. [Wait 500ms] → 6. Call reloadAllProjects() → 7. For each project:
  a. Save old handler and env
  b. Call loadProject()
  c. If success: use new handler
  d. If fail: restore old handler → 8. Remove deleted projects → 9. Log final project count

Data Structures

  • handlers (Map<string, Function>): Maps project names to their request handler functions
  • envs (Map<string, Record<string,string>): Maps project names to their environment variables
  • reloadTimeout (number | null): Stores the timeout ID for debouncing

Integration with Existing Code

The hot-reload feature integrates seamlessly with the existing Deno router:

  • The file watcher runs concurrently with Deno.serve() (using async/await pattern)
  • No changes needed to the request handling logic in Deno.serve()
  • Existing projects continue serving requests during reload (old handler remains until new one is loaded)
  • When a project is deleted, it's automatically removed from the routing table

API Interactions

Testing & Verification

Manual Testing Steps

  1. Deploy initial project: Deploy project A to a fresh runtime and verify it works with curl http://localhost:8080/project-a/
  2. Deploy second project: Deploy project B to the SAME runtime (without teardown). Verify B works AND A still works with curl http://localhost:8080/project-b/
  3. Modify project file: Edit a file in project A (e.g., change the response message). Wait ~500ms, then verify the change is picked up with curl http://localhost:8080/project-a/
  4. Deploy broken module: Deploy a module with a syntax error. Verify the old version still serves requests (no crash) and check logs for the error message
  5. Deploy multiple projects: Deploy to 3 projects simultaneously. Verify all 3 are routable within 5 seconds

Edge Cases

Edge Case Expected Behavior
Syntax error in new code Old handler continues serving, error logged
Circular import in new code Old handler continues serving, error logged
Deleted project directory Handler removed from routing table
Rapid file writes (deployment) Single reload after 500ms debounce
Project name starts with "_" Ignored (not reloaded)

Error Handling

  • Import failures: Old handler is preserved, error is logged via console.error()
  • Missing project.json: Caught in loadProject(), returns false
  • Invalid manifest: Caught by JSON.parse(), returns false
  • Wrong runtime type: Returns false (only loads "deno" or "bun")
  • No handler export: Returns false (requires export default)

Issues & Follow-ups

Known Limitations

  • No reload completion signal: The RFC mentioned an optional signal back to ingress when reload completes. This was not implemented as it was marked optional.
  • Full rescan on any change: Currently, any file change triggers a full rescan of all projects. This could be optimized to only reload the affected project.

Dependencies on Other Tasks

This task is independent of other tasks. However, it complements task 0010-1 ("Fix refresh() to restart runtime when projects remain") which would provide an alternative approach to runtime restarts.

Future Enhancements

  • Per-project reload: Instead of rescanning all projects on any change, only reload the affected project
  • Reload API endpoint: Add a /__reload endpoint (RFC Option B) for manual triggering
  • Reload status endpoint: Add an endpoint to check the reload status and last reload time
Note: The implementation fully satisfies the RFC requirements for Option A (recommended approach). All core features are implemented: file watching, 500ms debouncing, safe reload with old-handler fallback, and automatic cleanup of deleted projects.
