Task 0013-1: Move tunnel auth from URL to headers

Task Overview

  • Task ID: 0013-1
  • Title: Move tunnel auth from URL to headers
  • RFC: 0013-tunnel-header-auth
  • Status: Done
  • Commit: b56afef9 - "smithers: implement 0013-1 -- Add header-based tunnel auth with deprecation warning"

RFC Requirements

The RFC 0013 stated the following in its Next Steps section:

Implementation:
1. Add support for Authorization: Bearer <tunnel-id> header as an alternative to the URL path parameter
2. Poll and relay endpoints check the header first, fall back to URL parameter
3. For the WebSocket upgrade (RFC 0012), pass the token as a query parameter on the initial upgrade request only (this is standard for WebSocket auth since headers aren't supported in the browser WebSocket API)
4. Document the new auth method
5. Deprecation plan: log a warning when URL-based auth is used, remove in next major version

Why This Feature Matters

URL-based authentication exposes tokens in browser history, server logs, and referrer headers. While the 64-character hex tunnel ID is cryptographically unguessable, following security best practices by using HTTP headers for authentication prevents token leakage and provides a cleaner separation between the authentication mechanism and the request path.

Change 1: New function getTunnelIdFromRequest()

This new function extracts the tunnel ID from either the Authorization header (preferred) or the URL path (fallback).

+function getTunnelIdFromRequest(req: Request, urlTid: string): { tid: string; urlAuthUsed: boolean } {
+  // Check Authorization header first
+  const authHeader = req.headers.get("Authorization") || "";
+  if (authHeader.startsWith("Bearer ")) {
+    return { tid: authHeader.slice(7).trim(), urlAuthUsed: false };
+  }
+  // Fall back to URL path parameter
+  return { tid: urlTid, urlAuthUsed: true };
+}

Design Rationale: This function encapsulates the authentication logic and returns a flag indicating which method was used. The flag enables the deprecation warning while maintaining backward compatibility.

Design Decisions

Why Check Header First, Fall Back to URL?

  • Backward compatibility: Existing clients using URL-based auth continue to work without modification.
  • Gradual migration path: New clients can use header-based auth immediately, and the deprecation warning encourages others to migrate.
  • Clear deprecation signal: The warning log provides visibility into which clients are still using the deprecated method.

Why Use console.warn for Deprecation?

  • Server-side logging: The warning appears in server logs, making it visible to operators monitoring the system.
  • Non-breaking: Clients aren't rejected, so existing deployments continue to work.
  • Measurable: Log analytics can track adoption of the new header-based auth method.

Why the tid vs secret Property Name Fix?

  • Consistency: The server's tunnel creation endpoint has always returned tid as the property name.
  • Correctness: Using tunnel.secret (which is undefined) caused the "Secret" log message to show "undefined" even though the URLs were being constructed correctly with the path parameter.

How It Works

Authentication Flow

  1. Server receives request: The tunnel server handler receives a request at endpoints like /<tid>/poll, /<tid>/relay, or visitor paths.
  2. Extract tunnel ID: getTunnelIdFromRequest() is called:
    • First checks for Authorization: Bearer <tid> header
    • If found, returns the tid and sets urlAuthUsed: false
    • If not found, extracts from URL path and sets urlAuthUsed: true
  3. Deprecation check: If urlAuthUsed is true, logs a warning message.
  4. Validate tunnel: Looks up the tunnel in the tunnels Map using the extracted tid.
  5. Process request: Continues with normal request processing.

Client Authentication

  1. Create tunnel: Client POSTs to create a tunnel and receives the tid.
  2. Build URLs: Constructs pollUrl, relayUrl, and visitorUrl using the tid.
  3. Add Authorization header: All poll and relay requests include Authorization: Bearer ${tunnel.tid} header.
  4. Server validates: Server extracts tid from header (preferred method) without triggering deprecation warning.

Data Structures

Tunnel Interface:

interface Tunnel {
  tid: string;        // 64-character hex tunnel ID
  createdAt: number;  // Timestamp
  expiresAt: number;  // Expiration timestamp
  pollSeq: number;    // Poll sequence number
}

getTunnelIdFromRequest Return Value:

{ tid: string; urlAuthUsed: boolean }

Issues & Follow-ups

Known Limitations

  • URL-based auth still accepted: While deprecated, URL-based authentication still works. It will need to be removed in a future major version.
  • WebSocket auth not addressed: The RFC mentioned passing the token as a query parameter for WebSocket connections, but this implementation doesn't add WebSocket-specific handling. The apps/tunnel system uses HTTP polling, not WebSocket (RFC 0012's WebSocket implementation is in proxy/tunnel.py).
  • Logging only: Deprecation warning is only logged to console. In production, this should go to a proper logging system for monitoring adoption.

Dependencies

  • None: This task is independent of other tasks. It adds a new authentication method while maintaining backward compatibility.

Incomplete Items

  • Remove URL-based auth: Planned for next major version. No specific timeline set.
  • Documentation update: RFC requested documentation of the new auth method. This should be added to the project's developer guide.
