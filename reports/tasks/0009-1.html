Task 0009-1: Add health check endpoint and post-deploy verification

Task Overview

  • RFC: 0009-runtime-health-checks
  • Status: Done

What the RFC Asked For

From RFC 0009 - Implementation section:

"In proxy/runtimes.py, after refresh() starts a container, poll /_health with exponential backoff:
- First poll after 500ms
- Retry up to 10 times with 500ms, 1s, 1s, 2s, 2s, 4s... intervals
- Total timeout: 30 seconds
If health check passes, return success
If health check fails after 30s, return a clear error with the container logs"

Why This Feature Matters

Before this implementation, the ingress assumed the runtime container was ready immediately after starting. If the Deno container crashed on startup (e.g., due to a bad module import), the ingress would happily return 502 errors with no diagnostic information. This feature provides a readiness probe that:

  • Ensures the container is actually serving requests before reporting deploy success
  • Provides detailed error messages including container logs when startup fails
  • Prevents deployment of broken code from appearing to succeed

1. Added health_check() function (lines 247-286)

A new async function was added to poll the container's health endpoint with exponential backoff:

async def health_check(docker: DockerClient, cid: str, ip: str, port: int, timeout: float = 30.0) -> str:
    """Poll the container's health endpoint with exponential backoff.
    Returns container logs on failure, empty string on success.
    """
    intervals = [0.5, 0.5, 1.0, 1.0, 2.0, 2.0, 4.0, 4.0, 8.0, 8.0]
    total_elapsed = 0.0

    for delay in intervals:
        if delay > 0:
            await asyncio.sleep(delay)
            total_elapsed += delay
        else:
            # First poll after 500ms (initial interval)
            await asyncio.sleep(0.5)
            total_elapsed += 0.5

        try:
            async with aiohttp.ClientSession(timeout=aiohttp.ClientTimeout(total=5)) as session:
                async with session.get(f"http://{ip}:{port}/_health") as resp:
                    if resp.status == 200:
                        data = await resp.json()
                        if data.get("status") == "ok":
                            log.info("Health check passed for %s (uptime: %ds)", cid[:12], data.get("uptime", 0))
                            return ""
                    log.debug("Health check attempt %ds: status %d", total_elapsed, resp.status)
        except (asyncio.TimeoutError, aiohttp.ClientError) as e:
            log.debug("Health check attempt %ds: %s", total_elapsed, e)

        if total_elapsed >= timeout:
            break

    # Health check failed - get logs
    logs = await docker.logs(cid, tail=100)
    log.error("Health check failed for %s after %.1fs:\n%s", cid[:12], total_elapsed, logs)
    return logs

Design decision: The function returns an empty string on success and container logs on failure. This allows the caller to distinguish between success and failure without exception handling for the happy path. The exponential backoff intervals (0.5, 0.5, 1, 1, 2, 2, 4, 4, 8, 8 seconds) sum to 31 seconds, but the timeout check ensures we exit at 30 seconds.

2. Modified RuntimeManager._get_or_create() method (lines 376-384)

After starting a new container, the health check is called. If it fails, the container is cleaned up:

await self.docker.start(cid)
self.tracker.add(cid)
ip = await self.docker.container_ip(cid, network)

# Health check with exponential backoff (30s timeout)
logs = await health_check(self.docker, cid, ip, config["port"])
if logs:
    await self.docker.stop(cid)
    await self.docker.remove(cid, force=True)
    self.tracker.remove(cid)
    raise RuntimeError(
        f"Runtime container {cname} failed health check after 30s:\n{logs}"
    )

self.runtime_cids[key] = cid
self.runtime_ips[key] = ip

Design decision: If health check fails, the failed container is immediately stopped and removed to prevent leaving a broken container running. This prevents the container from being added to the tracking maps, ensuring the system can retry cleanly. The RuntimeError includes the container logs to help diagnose the failure.

Note on the Health Endpoint Implementation

The actual /_health endpoint in the Deno router was added in a prior commit (b7c19ef4, task 0008-1). It returns:

JSON.stringify({status: "ok", uptime: Math.floor((Date.now() - startTime) / 1000)})

This task 0009-1 added the polling logic to actually call this endpoint after deploy.

How It Works

Flow of a New Runtime Container Deployment

  1. Deploy request: A project is deployed via POST /_api/projects
  2. Runtime refresh: deploy.py calls rtm.refresh(runtime) (line 194)
  3. Container creation: RuntimeManager._get_or_create() creates and starts the Docker container
  4. Health check polling: health_check() is called with the container's IP and port
  5. Exponential backoff: The function polls http://<ip>:<port>/_health with increasing delays:
    AttemptDelayCumulative
    10.5s0.5s
    20.5s1.0s
    31.0s2.0s
    41.0s3.0s
    52.0s5.0s
    62.0s7.0s
    74.0s11.0s
    84.0s15.0s
    98.0s23.0s
    108.0s31.0s (timeout at 30s)
  6. Success path: On 200 OK with {"status":"ok"}, return empty string, container is added to runtime tracking
  7. Failure path: After 30s timeout or unrecoverable errors, fetch last 100 lines of logs and return them

Data Structures and APIs

  • Health endpoint response: {"status":"ok","uptime":<seconds>}
  • aiohttp ClientSession: Used for HTTP polling with 5-second per-request timeout
  • DockerClient.logs(cid, tail=100): Fetches container logs on failure
  • ContainerTracker: Healthy containers are added via self.tracker.add(cid), failed ones are removed

Integration with Existing Code

The health check integrates at a critical point in RuntimeManager._get_or_create(): between starting the container and registering it in the runtime maps (self.runtime_cids[key] and self.runtime_ips[key]). This ensures that only healthy containers are registered and can serve requests.

For existing containers (no restart needed), the health check is skipped entirely since the container is already known to be running.

Testing & Verification

Verifying a Healthy Deploy

Deploy a healthy application and verify:

  1. The deploy response comes AFTER the health check passes (not immediately)
  2. The logs show "Health check passed for <cid> (uptime: <seconds>)"
  3. Query the health endpoint directly: 
    curl http://<runtime-ip>:3000/_health
# Expected response: {"status":"ok","uptime":<seconds>}

Verifying a Failing Deploy

Deploy an application with a syntax error or bad import:

  1. The deploy returns a 500 error (or similar) with container logs
  2. The error message includes "Runtime container <name> failed health check after 30s:"
  3. The container is cleaned up (not left running)

Verifying Existing Container Behavior

Redeploy a different project while the runtime container is already running:

  1. The existing container should NOT be re-health-checked
  2. The deploy should complete quickly (no 30-second delay)

Edge Cases and Error Handling

  • Network errors during health check: Caught as aiohttp.ClientError, logged at DEBUG level, and retried with backoff
  • Timeout per request: 5-second timeout on each HTTP request to prevent hanging
  • Non-200 responses: Logged at DEBUG level, not treated as success
  • Malformed JSON response: Would cause resp.json() to fail, caught as aiohttp.ClientError
  • Missing "status":"ok" field: Treated as failure, logs show the actual status received

Issues & Follow-ups

Known Limitations

  • The health check only implements the happy path for Deno runtimes. Other runtimes (Node.js, Python, static, dockerfile) do not have health endpoints defined.
  • The health check timeout (30 seconds) is hardcoded. For slow-starting applications, this might be too short.
  • The exponential backoff is implemented with a fixed list of intervals rather than a calculated algorithm.
